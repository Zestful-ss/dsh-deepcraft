# D79. 会话级的插件状态：宿主的 domain 表单与官方策略

## 背景

一条会话可以有自己的子代理模型路由选择：它既不写进宿主的会话日志（插件不得往里追加宿主不认识的事件），也不该写进可清理的缓存目录（清缓存会悄悄改掉选择）。官方工具在会话组装时记下本会话「允许哪些路由」，这份记录只存在于宿主一侧的投影里，按会话对象读取，冷会话读不到。

同时，宿主没有已验证的接口可以在省略参数时替模型补上子代理模型；官方工具只在自己收到 `provider` 与 `model` 时才做允许列表校验。

## 决定

- 插件的每会话状态存放在宿主的数据域表单里：插件自己的域名、一个版本号、一张按会话 id 作键的表，记录用 Zod 模式声明；读是同步的，写落盘之后才返回。数据落在 `$DSH_HOME/storages/<域名>.json`，不追加到会话日志。
- 落盘只经由插件自己的私有路由，服务端按会话核验：会话必须是本进程里打开的，写入的每一对 `provider` / `model` 必须同时出现在该会话官方的允许列表里，否则拒绝；清空用空列表表示，记录随之删除。路由与守卫读同一份记录，页面不自行判断允许什么。
- 规则只拒绝、不改写调用参数：省略、只写一半、或写了选择之外的路由都被拒绝，并把可用路由写进拒绝理由；显式选中的路由以及主模型自己的那条照常放行。宿主提供的注入点出现之前，不替模型挑路由，也不假装重试一定会发生。
- 选择先于一层的开关：一条会话存有选择时，即使全局「必须选择模型」的开关是关的，规则照旧生效；没有选择时，规则回到该开关本来的语义。
- 记录读不出来与「没有选择」区分开：存储存在却读不出、或存下的路由已不在官方允许列表里，都明确报告；只有宿主根本没有存储服务时才当作没有选择，以免整套委派被一个不存在的服务拦下。

## 后果

- 选择按会话保存，与官方策略的快照同时生效：官方设置改动只影响后来创建的会话，已有会话的选择与允许列表都不被改写。
- 规则覆盖官方 `subagent` 工具的执行；`subagent_fork`、工作流、团队模式以及其他插件直接调用 `subagents.startActivation` 的路径不经过这道守卫，不能承诺被覆盖。
- 页面上看到的是宿主的答复，不是自己的推断：允许列表、已保存的选择、不可用的原因都由路由给出，写失败时页面保留上一次保存的选择并说明没有保存成功。
- 放弃的方案：把选择写进会话日志（插件不得追加宿主未知事件）；把选择放进可清理的缓存目录（清缓存即丢失，且与「按会话保留」矛盾）；在缺少参数时由守卫替模型补一个路由（宿主没有注入点，补参数等于伪造模型的决定）。

## 重审条件

- 宿主提供在工具执行前注入参数的正式接口时，规则改为注入并说明，不再只靠拒绝。
- 宿主把官方的允许列表投影成可冷读、可按 id 读取的形式时，会话 id 即可核验，私有路由不再需要「会话必须已打开」这一条。
- 宿主对插件数据域提供按会话分区的存储形态时，表键改为分区键，记录格式随之下沉。
